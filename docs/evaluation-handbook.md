# 1. 네트워크 설계와 보안 기준

## 구성 예시
VPC: 10.10.0.0/16 / Public Subnet: 10.10.1.0/24 / 단일 AZ
EC2: Amazon Linux 2023, 공인 IPv4 할당, Nginx 사용
이름 예시: aws-mini-test-vpc / aws-mini-test-public-a / aws-mini-test-web
태그 예시: Project=AWS-mini-test, Owner=<실습자>, ExpiresAt=<정리일>

```text
외부 클라이언트 (HTTP 80)       관리자 공인 IP/32 (SSH 22)
              |                         |
              +---------- Internet -----+
                             |
                    Internet Gateway
                             |
       VPC 10.10.0.0/16 / Public Subnet 10.10.1.0/24
          연결 Route Table: 0.0.0.0/0 -> IGW
                             |
            Security Group -> EC2 공인 IPv4
                               Nginx :80 /health
```

IGW는 VPC와 인터넷을 연결한다. IPv4 인터넷 통신에는 EC2의 공인 IPv4 또는 EIP, 서브넷에 연결된 IGW 경로, 허용된 SG·NACL, 동작 중인 서버가 함께 필요하다. Route Table은 패킷이 통과하는 별도 서버가 아니라 서브넷의 경로 규칙이다. [1]

## 라우팅
10.10.0.0/16 -> local: VPC 내부 통신용 경로.
0.0.0.0/0 -> IGW: 더 구체적인 경로가 없는 외부 IPv4 목적지로 보낼 기본 경로. 반드시 해당 Public Subnet에 연결된 Route Table인지 확인한다. 공인 IP만 있어도 인터넷 연결이 되는 것은 아니다. [1]

## 보안 그룹 인바운드
- TCP 22: 관리자 현재 공인 IPv4/32만 허용. 사설 IP나 EC2 공인 IP를 입력하지 않는다.
- TCP 80: 공개 웹 검증이면 0.0.0.0/0. 지정 평가자만 접근할 경우 평가자 IP/32로 축소 가능.
- TCP 443: TLS를 구성한 경우에만 추가. 이번 HTTP 예제에서는 추가하지 않는다.
- TCP 3306/5432 및 기타 포트: 미허용. DB가 필요하면 Private Subnet과 애플리케이션 SG 참조를 사용한다.

SG는 허용 규칙을 사용하고 상태를 추적하므로 허용된 요청의 응답 트래픽을 별도 인바운드 규칙으로 열 필요가 없다. 아웃바운드는 패키지 설치 등 필요한 통신을 고려해 별도로 설명한다. NACL은 상태를 추적하지 않으므로 커스텀 설정이면 반환 포트도 확인한다. [2]

# 2. 실습 절차와 접속 검증

## 구성 순서
1. 실습용 VPC와 Public Subnet을 만들고 이름·태그를 붙인다.
2. IGW를 VPC에 연결한다. 전용 Route Table에 0.0.0.0/0 -> IGW를 추가하고 Public Subnet을 명시적으로 연결한다.
3. SSH 22를 관리자 IP/32로, HTTP 80을 검증 대상 범위로 허용하는 SG를 만든다.
4. 해당 서브넷에 Amazon Linux 2023 EC2를 생성한다. 공인 IPv4, 키 페어, SG 연결 상태를 확인한다. EIP는 선택 사항이며 검증만을 위해 필수는 아니다.
5. 로컬 터미널에서 아래 SSH 예시로 접속한다. 키 경로와 공인 IP는 실제 값으로 바꾼다.

```text
ssh -i <키파일.pem> ec2-user@<EC2_PUBLIC_IP>
```

## EC2 내부에서 웹 서버 설정
아래는 새 실습 서버의 기본 설정 예제다. 기존 서비스가 있는 서버에 그대로 덮어쓰지 않는다. 셸 명령은 EC2의 Bash에서 실행한다.

```bash
sudo dnf install -y nginx
sudo tee /etc/nginx/nginx.conf >/dev/null <<'EOF'
events {}
http {
server {
    listen 80;
    server_name _;
    location = /health {
        default_type text/plain;
        return 200 "AWS-mini-test OK\n";
    }
    location / {
        default_type text/plain;
        return 200 "AWS-mini-test web server\n";
    }
}
}
EOF
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
curl -i http://127.0.0.1/health
```

이 예제는 새 실습 서버의 nginx.conf 전체를 최소 설정으로 교체한다. 기존 설정이 필요하면 먼저 사본을 보존한다. nginx -t가 성공한 경우에만 시작·재시작·reload를 진행한다.

## 외부 PC에서 검증
B 방식(기본): `curl.exe -i --max-time 10 http://<EC2_PUBLIC_IP>/health` (Windows). macOS/Linux에서는 curl을 사용한다. 기대값은 HTTP 200과 본문 `AWS-mini-test OK`다. 상태 코드만 200인 경우 고정 본문까지 확인한다.
A 방식(대안): 브라우저에서 `http://<EC2_PUBLIC_IP>/`를 열어 페이지·주소를 함께 촬영한다. HTTPS로 자동 전환되지 않았는지 확인한다.

# 4. 구술 평가 예상 질문·답변

## 항목 2 답변 예시
2-1. 외부 요청은 EC2의 공인 IPv4를 대상으로 IGW를 통해 VPC로 들어오고, 서브넷·SG·호스트 설정이 허용할 때 EC2 웹 서버에 도달합니다. 응답은 서브넷 Route Table의 IGW 기본 경로로 나갑니다. 다이어그램에서 경로와 접근 제어를 구분해 설명하겠습니다.

2-2. 관리에는 22번, 이번 HTTP 검증에는 80번만 필요합니다. SSH는 관리자 IP/32로 제한했습니다. TLS와 DB를 구성하지 않았으므로 443·3306·5432는 열지 않았습니다. HTTP의 전체 공개는 웹 제공 목적에 따른 결정이며 SSH 전체 공개와 목적이 다릅니다.

2-3. B 방식을 선택하면 상태 코드와 고정 응답을 명령으로 재확인할 수 있습니다. Nginx에 /health를 만들고 외부 PC에서 HTTP 200과 지정 본문을 확인합니다. A를 선택했다면 루트 페이지와 브라우저 정상 로딩을 근거로 설명합니다.

2-4. Project·Owner·ExpiresAt 태그와 공통 이름 접두사를 사용합니다. 태그 검색만 믿지 않고 리소스 ID와 리전을 목록에 남깁니다. 생성 즉시 목록에 추가하고 정리 후 최종 상태와 확인 시각을 기록합니다.

## 항목 3 답변 예시
3-1. local 경로는 VPC 내부 통신만 처리합니다. 외부 IPv4 목적지로 응답하려면 IGW를 가리키는 기본 경로가 필요합니다. 더 구체적인 경로가 있으면 그 경로가 먼저 선택됩니다. 서브넷 연결과 IGW의 VPC 연결도 함께 확인합니다. [1]

3-2. SG는 연결된 리소스의 네트워크 트래픽을 제어하고, IAM은 누가 어떤 AWS API 작업을 어떤 리소스에 할 수 있는지 제어합니다. SG에 22번을 열어도 IAM 권한이 생기지 않고, IAM 권한이 있어도 OS 로그인 자격이 자동으로 생기지 않습니다. 최소 권한은 실수나 계정 침해의 영향 범위를 줄입니다. [2, 3]

3-3. SSH·DB를 0.0.0.0/0에 공개하면 인터넷 전체에서 스캔과 인증 공격을 시도할 수 있습니다. SSH는 관리자 IP/32 또는 VPN, 관리 목적에는 Session Manager를 검토합니다. Session Manager는 에이전트·IAM 역할·서비스 연결을 준비해야 합니다. DB는 Private Subnet에서 앱 SG만 허용합니다. 본 평가에서 요구하는 SSH 증빙과 관리 대안 설명은 구분합니다.

3-4. 여러 설정을 동시에 바꾸면 원인을 특정하기 어렵습니다. 예를 들어 '라우트 누락'이라는 가설을 세운 뒤 실제 연결 Route Table을 확인하고, 수정 전후 동일 요청을 비교합니다. 명령·시간·오류·로그를 남기면 원인과 조치의 관계를 설명할 수 있습니다.

답변은 예시다. 실제 사용한 IP 범위·검증 방식·리소스 이름에 맞춰 수정하고, 수행하지 않은 작업을 수행한 것처럼 말하지 않는다.

# 5. 장애 대응·확장·비용 시나리오

## 외부 접속 실패: 점검 순서
1. 라우팅: EC2가 속한 서브넷의 실제 연결 Route Table, 0.0.0.0/0 -> IGW, IGW의 VPC 연결을 확인한다.
2. SG: EC2 ENI에 연결된 SG에서 HTTP 80, SSH 22와 접속자의 실제 공인 IP를 확인한다. 커스텀 NACL이 있으면 양방향 통신도 확인한다.
3. 공인 IP/DNS: 현재 EC2의 공인 IP와 URL을 대조한다. 중지·시작 후 자동 할당 IP가 바뀔 수 있다. DNS를 썼다면 현재 IP로 해석되는지 확인한다.
4. 프로세스/로그: `sudo systemctl status nginx`, `sudo ss -lntp`, `sudo nginx -t`, `sudo tail -n 50 /var/log/nginx/error.log`로 실행·리스닝·설정·오류를 확인한다. 호스트 방화벽도 확인한다.

타임아웃은 경로·필터링 가능성, 연결 거부는 리스닝·방화벽 가능성, HTTP 404는 경로·가상호스트 가능성을 시사한다. 오류 문구만으로 단정하지 말고 해당 계층에서 근거를 확보한다.

## IAM 권한 부족
AccessDenied의 작업명·대상 ARN·리전·호출 주체를 기록한다. 가능한 경우 CloudTrail의 실패 이벤트로 요청을 확인한다. 기존 정책과 명시적 Deny, permissions boundary, SCP 등 제약을 검토한다. 필요한 Action·Resource·Condition만 제안하고 허용 가능한 관리자 절차로 적용한 뒤 동일 작업을 재검증한다. 리소스 수준 권한을 지원하지 않는 API는 그 제약을 설명한다. 관리자 전체 권한을 즉시 부여하는 방식은 사용하지 않는다. [3]

## 인스턴스 2대로 확장
단일 EC2는 장애 지점이며 CPU·메모리·연결 수·앱 상태가 병목일 수 있다. 지표로 병목을 먼저 확인한다. 인터넷용 ALB와 Target Group을 추가하고 서로 다른 AZ의 EC2 2대로 분산한다. 일반적인 ALB 구성에는 서로 다른 AZ의 서브넷 2개가 필요하다. EC2 앱 포트는 ALB SG에서만 허용한다. /health 헬스 체크와 Auto Scaling을 고려하고 세션·업로드 파일을 인스턴스 외부로 분리한다. ALB만으로 DB 병목까지 해결되는 것은 아니다. [5, 6]

## 예상치 못한 비용
Billing/Cost Explorer에서 기간·서비스·리전·사용 유형으로 범위를 좁힌다. 실행 중인 EC2, 남은 EBS·스냅샷, 공인 IPv4/EIP, 추가한 NAT Gateway·ALB, 로그 저장량·데이터 전송을 점검한다. 태그와 리소스 ID로 실습 자원을 대조한다. EC2를 중지해도 모든 비용이 사라지는 것은 아니다. 정리 뒤 목록 재조회와 후속 비용 확인을 모두 수행하며 비용 집계 지연을 고려한다. [4]

## 정리 절차와 체크리스트
실습용 자원만 식별하고 필요한 데이터 보존 여부를 확인한 후 진행한다. 아래는 기록 양식이며 실제 정리를 수행했다는 뜻이 아니다.

- EC2: 종료(terminate) 상태 확인. 중지(stop)만으로 완료 처리하지 않는다. ID ______ 상태 ______ 시각 ______
- EBS: 종료 시 자동 삭제 설정에만 의존하지 말고 잔존 볼륨을 조회한다. 보존 불필요한 실습 볼륨 삭제 확인. ID ______ 결과 ______
- EIP: 사용했다면 연결 해제 후 할당 해제(release) 확인. 미사용이면 '미생성, 할당 목록 확인'으로 기록한다. ID/미사용 ______ 결과 ______
- IGW: 사용 중 자원 정리 후 VPC에서 분리하고 삭제 확인. ID ______ 결과 ______
- VPC: 서브넷·비기본 SG·사용자 Route Table 및 기타 종속 자원을 정리한 후 삭제 확인. ID ______ 결과 ______
- 추가 자원: 만든 경우 NAT Gateway, ALB, ENI, 스냅샷, 로그 그룹 등을 별도 확인. 목록 ______ 결과 ______

EC2 종료 시 EBS의 보존 여부는 볼륨의 DeleteOnTermination 설정에 따라 다르며, EIP는 연결 해제와 할당 해제가 다르다. EIP를 만들지 않았다면 삭제 완료로 허위 표기하지 않는다. 평가자가 5종 모두 실제 삭제 증빙을 요구하는 경우 미사용 항목 처리 기준을 먼저 맞춘다. [4]
